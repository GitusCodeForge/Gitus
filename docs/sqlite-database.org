** resolving path specified in config

All db path, when they're relative path (currently determined by `path.IsAbs` in go), are resolved against the residing directory of *the config file*.

** "database is locked" error

See:

https://github.com/mattn/go-sqlite3/issues/39
https://github.com/mattn/go-sqlite3/issues/209

and:

https://stackoverflow.com/questions/57118674/go-sqlite3-with-journal-mode-wal-gives-database-is-locked-error

#+begin_quote
As part of opening the database, go-sqlite3 will execute PRAGMA statements to set various defaults. One of these defaults is setting the journal_mode=DELETE. However, if another process has the database opened, the mode cannot be changed back to DELETE. Executing this statement fails with "database is locked" and so you will see the open operation fail with that error.
#+end_quote

The current method is:

+ No =db.SetMaxOpenConns(1)= since we rely on multiple open connection.
+ The string =?cache=shared&mode=rwc&_journal_mode=WAL= is added to sqlite db path.

Please note that while all =.Query= should've already had their corresponding =.Close= deferred, =.QueryRow=, which returns a =*sql.Row=, does not seem to provide a =.Close=. The decision above is made when all =.Query= are properly closed and all transaction properly =.Rollback=-ed or =.Committed= and the program still has "database is locked" error.

** prepared statements and the statement cache

Every query goes through =(*SqliteGitusDatabaseInterface).prepare= or
=.prepareTx= (see =defs.go=), which keep the compiled statements in a map on
the interface instance. Statements returned by the cache are owned by the
cache and must *not* be closed by the caller; =Dispose= finalizes them.

This is not only an optimization. =sql.DB.Prepare= hands out a new
=*sql.Stmt= on every call, and the underlying =sqlite3_stmt= stays alive until
that statement is finalized. The earlier code prepared a statement for every
single query and rarely closed it, so every request leaked a little:
2000 calls of =GetUserByName= grew the heap by roughly 1.6MB before the cache
was introduced.

Statements prepared from a =*sql.Tx= are finalized together with the
transaction by =database/sql= itself, but they still go through =.prepareTx=
so that the per-connection statement cache is reused instead of recompiling
the same SQL for every transaction.

When adding a query, keep in mind that the cache is keyed by the full SQL
text: never build SQL whose number of placeholders varies with the input
(e.g. an =IN (?,?,...)= list). =ResolveMultipleEmailToUsername= builds
exactly such a query and deliberately uses =connection.Query= directly.

Most listing queries are assembled by =db.QueryBuilder=
(=pkg/gitus/db/builder.go=): conditions and their arguments are added
together, and the builder renders either =?= (sqlite) or =$n= (postgres) for
the placeholders. The column lists and the matching row scanners live in
=sqlaux.go= next to the query code.
