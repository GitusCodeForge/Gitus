* notes on pull-request

a pull request is purely an "external" construct that only exists in the eyes of the surrounding tools (in this case, Gitus itself). something like this is to be used:

#+begin_src sql
  DROP TABLE IF EXISTS gitus_pull_request;;
  CREATE TABLE IF NOT EXISTS gitus_pull_request (
      username TEXT,
      pull_request_id INT,
  	title TEXT,
      -- the receiving repo
      receiver_namespace TEXT,
  	receiver_name TEXT,
  	receiver_branch TEXT,
  	-- the repo you're pulling from
  	provider_namespace TEXT,
  	provider_name TEXT,
  	provider_branch TEXT,
  	-- in json.
  	merge_conflict_check_result TEXT,
  	merge_conflict_check_timestamp INT,
  	-- 1 - open.
  	-- 2 - closed (merged) 
  	-- 3 - closed (not merged)
  	pull_request_status INT,
  	pull_request_timestamp INT,
  	FOREIGN KEY (username) REFERENCES gitus_user(user_name)
  );;
  DROP TABLE IF EXISTS gitus_pull_request_event;;
  CREATE TABLE IF NOT EXISTS gitus_pull_request_event (
      pull_request_abs_id INTEGER,
  	-- 1 - normal comment.
  	-- 2 - comment on code.
  	-- 3 - update on provider branch.
  	-- 4 - merge conflict check.
  	-- 5 - close as not merged.
  	-- 6 - close (merged).
  	-- 7 - reopen
  	event_type INTEGER,
  	event_timestamp INTEGER,
  	event_author TEXT,
  	event_content TEXT,
  	FOREIGN KEY (pull_request_abs_id) REFERENCES gitus_pull_request(rowid)
  )

#+end_src


** merge conflict check

merge conflict check is currently done by using these two commands:

+ =git fetch {remote} {branch}=: fetch fork updates
+ =git merge-tree {self} {pull_source}=: check for possible merge conflict


*** conflicted file info

the conflicted file info line seems to be formatted as follows:

+ file mode (within the tree), 6 characters ascii of octal digits.
+ one (1) space.
+ the object id of the file, in ascii hex string.
+ one (1) space.
+ a "stage". seems to be in ascii of digits.
+ one (1) tab.
+ file name of the file which has the conflict.

as stated in [[https://git-scm.com/docs/git-merge-tree#OUTPUT][the document of git-merge-tree]] only the file name would be returned if the =--name-only= option is passed. the file name would be quoted if the config =core.quotePath= is set to true (which is the default value) and you don't provide the =-z= option to git-merge-tree, so it's better to use the =-z= option, with which there is no quoting and the file name part can be used as-is.


** merge methods

the pull request page offers three merge methods when a pull request has a
successful merge check:

| method   | result                                                           |
|----------+------------------------------------------------------------------|
| =merge=  | a merge commit with the receiver branch and the provider branch as parents |
| =squash= | a single commit whose tree is the merge result; its only parent is the receiver branch and its subject is the pull request title |
| =rebase= | the provider commits are replayed one by one onto the receiver branch |

=squash= leaves the provider commits out of the receiver's history; =rebase=
keeps them but rewrites their ids. the replayed commits keep their original
author and author date; the committer is the user who clicked merge.

the merge check itself is a single 3-way merge, so it only answers "does the
final tree conflict?". =rebase= can additionally fail on an intermediate
commit even when the final tree merges cleanly; in that case the merge is
reported as failed and the receiver branch is left untouched. commits that
would become empty during a rebase are dropped, like =git-rebase= does.

the method used is recorded in the "closed as merged" pull request event and
shown on the pull request page.

** reviews

a pull request can have any number of reviewers. the author can add reviewers;
maintainers (the repository or namespace owner, administrators, and members
with an administrative ACL privilege) can also add and remove them. only
maintainers can remove a reviewer: the author must not be able to remove a
reviewer who asked for changes. being allowed to add repositories to the
namespace is not enough for this. the author of the pull request cannot be a
reviewer and cannot approve it.

each reviewer either approves or requests changes. the current state is kept in
a separate table so the merge check can read it directly:

#+begin_src sql
  CREATE TABLE IF NOT EXISTS gitus_pull_request_review (
      pull_request_abs_id INTEGER,
      reviewer TEXT,
      review_status INTEGER,   -- 0 pending, 1 approved, 2 changes requested
      reviewed_commit TEXT,    -- provider branch tip the reviewer looked at
      review_timestamp INTEGER,
      UNIQUE (pull_request_abs_id, reviewer)
  )
#+end_src

a pull request without reviewers is merged as before. as soon as a reviewer is
assigned, every reviewer must have approved the exact provider commit that is
about to be merged; a pending reviewer or a requested change blocks the merge.
the approval records the commit id, so a new push to the provider branch makes
the old approvals stale instead of silently applying them to unreviewed code.
the reviewer has to approve again (the page marks an approval for an older
commit). the database checks this again inside the merge call, after the
provider branch has been fetched, so hiding the merge form is not the only
guard.

** merge

Gitus deals with bare repository so common commands like =git-merge= will not work. Fortunately Git documentation provides an example for using the low-level "plumbing commands" (as per Git lingo). The process shall goes as follows:

+ (=$provider= would be =$providerRemote/$providerBranch=, e.g. with branch "myBranch" of remote "myRemote", =$provider= would be =myRemote/myBranch=.)
+ =git merge-tree --write-tree $receiverBranch $provider=
  + The command line option =--write-tree= must be present. If this is not present, =git merge-tree= would only perform a dry-run with no trees being actually merged and written into the repo. Use =--write-tree= if you need to write the merged result to the repo. The output is the same for both - if the merge is conflict free, the id of the resulting tree would be written to stdout.
+ =git commit-tree $TREEID -m {message} -p $receiverBranch -p $provider=
  + This writes the commit to the repo and write the commit id to stdout.
  + This command needs to have the following envvar set:
    + =GIT_AUTHOR_NAME=
    + =GIT_AUTHOR_EMAIL=
    + =GIT_COMMITTER_NAME=
    + =GIT_AUTHOR_EMAIL=
+ =git update-ref $receiverBranchFullName $commitId=
  + =$receiverBranchFullName= must be "local full name", i.e. the one that starts with =refs/=. For any local branch =$branch=, this would be =refs/heads/$branch= (e.g. the local full name of branch =myLocal= would be =refs/heads/myLocal=).

=squash= is the same =merge-tree= step followed by a =commit-tree= with only the
receiver branch as parent.

=rebase= walks =git rev-list --reverse --no-merges $receiverBranch..$provider=
and, for every commit, runs =git merge-tree --write-tree --merge-base=$commit^
$newTip $commit= to get the cherry-picked tree, then writes it with
=git commit-tree= using the original author and message. the receiver branch is
only updated after every commit has been replayed, so a conflict in the middle
of the series cannot leave a half-rebased branch behind.
